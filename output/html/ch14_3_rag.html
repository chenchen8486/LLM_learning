14.3 RAG：给模型外挂一个资料库

本页范围：第 14 章第 3 节　|　整理时间：2026-10-10

快速浏览

核心问题模型权重训练收官就冻结：知识有截止日期，够不着训练语料之外的私有文档，不懂的问题也敢硬答（幻觉）。不改一个参数，能不能让模型回答时「现查资料」？查到的资料又怎样进入模型的输入？
本节主张RAG（检索增强生成）把「记住知识」与「使用知识」解耦：参数记忆留在权重里管语言能力，非参数记忆搬到模型外落成向量资料库管事实知识。回答前先按问题的向量检索出最相关的文档块，拼进 prompt，模型在新鲜、专属的资料上生成——权重一个没动，知识随改随生效，还能指明出处。
一句话结论RAG 的全部魔法就是「推理之前先查资料，再把资料拼进输入」；它由检索器（DPR 双编码器）与生成器两部分组成，效果上限由检索质量决定，失效也大多发生在检索一侧。

　　前两节（14.1 的 prompt 工程、14.2 的思维链）都在「怎么问」上做文章：换 prompt 写法、让模型把中间步骤写出来，模型的知识存量一分没增。本节换个方向，处理另一类短板——模型「不知道」的问题。先打个比方：训练收官的模型像一个刚交卷的闭卷考生，脑子里的知识冻结在收卷那一刻；之后世界发生的新事、别人手里的私有资料，他都无从知晓，被追问时还可能凭语感现编一个听起来像样的答案。RAG 的思路就是把闭卷改成开卷：回答之前，先让他翻资料。

　　本节按「动机 → 原论文（Lewis et al., 2020，RAG 原始论文）→ 工程实践 → 失效模式」的顺序展开，路线图如下：

  1. 为什么需要外挂：参数记忆的三个短板（14.3.1）：知识截止、私有知识、幻觉——焊死在权重里的知识为什么不够用；
  2. RAG 原论文结构：检索器 DPR 与生成器（14.3.2）：2020 年的原始设计，问题编码 → 检索 → 拼接进上下文的完整推导，RAG-Sequence 与 RAG-Token 两种形式；
  3. 工程链路：切块、嵌入、向量库、召回、重排、塞进 prompt（14.3.3）：今天的标准做法，六步流水线逐步拆解；
  4. RAG 的失效模式（14.3.4）：检索不到、切坏上下文、噪声混入——挂了资料库也救不了的三种典型翻车。

14.3.1 为什么需要外挂：参数记忆的三个短板

　　把「不知道」拆开看，参数记忆（存在模型权重里的知识）有三个绕不开的短板：

  1. 知识截止。训练语料有时间断面（第 1 章），权重里的知识也就冻结在那一刻。之后的新产品、新人事、新论文，模型一概不知。靠重新训练追新不现实：第 7 章算过账，一次预训练的算力开销巨大，不可能天天重跑。
  2. 私有知识。企业内部文档、个人笔记、未公开的数据从没进过训练语料，再强的模型也不可能背出它没见过的东西。靠微调把私有知识灌进权重，既贵又慢，改一条就要动一次训练。
  3. 幻觉。语言建模的训练目标（第 6 章）只奖励「说得像人话」，不奖励「说的是真的」。模型对不了解的领域同样下笔流利，自己分不清哪句来自记忆、哪句是现编，也给不出任何出处。

　　三条短板同根同源：知识焊死在参数里。焊死的东西有两个通病——改不动（更新一条知识要动权重，牵一发动全身）、查不着（说不清某句话的依据是什么）。RAG 论文（Lewis et al., 2020）给出的破局框架，是把记忆拆成两半：参数记忆（parametric memory）继续留在权重里，管语言能力与推理；非参数记忆（non-parametric memory）搬到模型外面，落成一座可检索的资料库，管事实知识。资料库的内容随改随生效，还能逐条指明出处。

检索增强生成 RAG Retrieval-Augmented Generation = 检索 + 增强 + 生成：先检索资料，再让生成有据可依

一类系统的统称：回答之前，先按问题去外部资料库检索最相关的内容，把检索结果与原问题一起拼进模型输入，再让模型基于这些新鲜、专属的资料生成回答。全过程中模型权重一个参数都不动——改变的是输入，不是模型。名字里的「增强」指的就是检索到的资料对输入的增强。

闭卷考试改开卷考试：考生（模型）还是那个人，水平没变，但允许他进场翻资料。冷门题目的正确率立刻上去，而且每道题都能注明翻的是哪本书。
分工原则一句话：知识与能力分开存放——语言与推理能力留在参数里，靠训练获得（第 6–11 章）；事实知识放进外部资料库，靠检索取用。模型不必把全世界背下来，会查就行。

14.3.2 RAG 原论文结构：检索器 DPR 与生成器

　　RAG 这个名字来自 Lewis 等人（Facebook AI）2020 年发表在 NeurIPS 的论文（arXiv:2005.11401），标题点明了它的战场：知识密集型 NLP 任务。论文的结构干净利落，只有两大件：检索器负责从资料库里找出相关文档，生成器负责读文档写答案。一次问答走三步：问题编码 → 检索 → 拼接进上下文。

　　检索器用的是同一团队稍早提出的 DPR（Dense Passage Retrieval，arXiv:2004.04906，EMNLP 2020），核心是双编码器：问题编码器 \(q(\cdot)\) 与文档编码器 \(d(\cdot)\) 是两个独立的 BERT-base 模型，各自把一段文本压成一个 768 维向量（取 [CLS] 位置的表示，[CLS] 是 BERT 输入最前端的特殊标记，其输出向量常被当作整段文本的语义摘要）。问题与文档的匹配程度用两个向量的内积衡量，全体文档上的归一化形式是：

\[ p_\eta(z \mid x) \;=\; \frac{\exp\!\big(d(z)^{\top} q(x)\big)}{\sum_{z'} \exp\!\big(d(z')^{\top} q(x)\big)} \tag{1} \]
公式 (1)：检索分布——文档块与问题的向量内积越大，被检索到的概率越高。符号说明：\(x\) 是用户问题；\(z\) 是资料库中的一个文档块；\(q(\cdot)\) 是问题编码器，输出 768 维向量；\(d(\cdot)\) 是文档编码器，与 \(q\) 互相独立；\(d(z)^{\top} q(x)\) 是两个向量的内积，语义越相近分越高；\(\eta\) 代表检索器的参数。分母是对全库文档的归一化，实际系统不算它——内积本身就能排序，直接取前 \(k\) 名即可（这一步叫最大内积搜索 MIPS，由 FAISS 这类向量索引加速）。
注释：BM25 是关键词时代的主流检索算法（Lucene / Elasticsearch 的默认打分），靠词频与逆文档频率做字面匹配，不懂语义——「猫」和「喵星人」在它眼里是两个无关词。DPR 这类稠密检索把文本压进语义向量空间（3.1 节的词嵌入思想从词推广到段落），措辞不同但意思相近也能匹配上。DPR 论文报告：在多个开放域问答数据集上，top-20 命中率比 BM25 高 9–19 个点。开放域问答指不限定依据文档、直接对大语料库提问的问答形式。

　　RAG 论文的资料库是 2018 年 12 月的英文维基百科，切成 2100 万个互不重叠的 100 词块，每块经文档编码器得到一个 768 维向量，全部向量用 FAISS 建成索引。生成器是 BART-large（约 4 亿参数的编码器-解码器结构，第 4 章架构家族的成员）：把问题与检索到的文档块拼在一起作为输入，逐 token 生成答案。有一个工程取舍值得记住：训练时文档编码器与索引冻结不动——2100 万个向量重算一遍太贵；被训练的只有问题编码器与生成器，两者端到端联训。索引建成后，资料库对训练而言就是一张只读大表。

　　检索结果怎么参与生成？论文给了两种形式，差别在边缘化（把「依据哪份资料」这个隐变量加权平均掉）发生在哪一级。第一种 RAG-Sequence 让整段回答共用同一份检索结果：

\[ p_{\mathrm{RAG\text{-}S}}(y \mid x) \;\approx\; \sum_{z \in \mathrm{top\text{-}k}} p_\eta(z \mid x)\, p_\theta(y \mid x, z) \tag{2} \]
公式 (2)：RAG-Sequence——在序列级做加权，一份检索结果决定整段回答。符号说明：\(y\) 是完整回答；\(\theta\) 是生成器（BART-large）的参数；\(p_\theta(y \mid x, z)\) 是给定问题与某一个文档块时生成整段回答的概率；\(\mathrm{top\text{-}k}\) 是公式 (1) 召回的前 \(k\) 个文档块；求和把「答案依据哪份资料」按检索概率 \(p_\eta\) 加权平均掉。

　　第二种 RAG-Token 把加权下放到每一个 token：

\[ p_{\mathrm{RAG\text{-}T}}(y \mid x) \;\approx\; \prod_{i=1}^{N} \sum_{z \in \mathrm{top\text{-}k}} p_\eta(z \mid x)\, p_\theta(y_i \mid x, z, y_{<i}) \tag{3} \]
公式 (3)：RAG-Token——在 token 级做加权。符号说明：\(N\) 是回答的 token 数；\(y_i\) 是第 \(i\) 个 token；\(y_{<i}\) 是已经生成的前 \(i-1\) 个 token；其余符号同公式 (2)。连乘号里面套着求和号：每生成一个 token 都重新对 \(k\) 个文档块做一次加权，于是不同 token 可以援引不同文档。

图 3：RAG 两种生成形式的对照。左图 RAG-Sequence：每个文档块各自支撑一个完整的候选回答，最后按检索权重求和（Σ）得到整段答案的概率，求和发生在序列级；右图 RAG-Token：每生成一个 token（y₁ 到 y₄）都重新对三个文档块做一次加权，深紫色块是该 token 的主导资料，不同 token 可以援引不同文档，求和钻进了连乘号内部。

　　值得一提的是，今天的实际系统大多按 RAG-Sequence 的精神做简化执行：检索一次 top-k、拼进上下文、生成交给大模型——公式 (2) 里那笔边缘化的细账，交给大模型在阅读上下文时自己消化，不再显式求和。原论文在开放域问答上取得了当时最佳的成绩，人工评估还显示 RAG 生成的答案比纯参数模型更具体、更有事实依据。

密集段落检索 DPR Dense Passage Retrieval = 用稠密向量做段落级检索

双编码器检索器：问题与文档各走一个 BERT-base，压成 768 维向量，内积即匹配分。训练用对比学习：一个问题配若干正确文档为正样本，同批次其他问题对应的文档充当负样本（批内负样本），目标是拉近正样本对的内积、推远负样本对。「稠密」对应「稀疏」：BM25 的词袋表示又高又稀疏（词表多大向量就多大），DPR 的 768 维向量紧凑稠密。

图书馆的两种找书法：BM25 按书名关键词逐字比对；DPR 像一位懂内容的馆员，按「讲的是什么」找书，换个问法也找得到。

14.3.3 工程链路：切块、嵌入、向量库、召回、重排、塞进 prompt

　　原论文的端到端联训漂亮但门槛高。今天的工程实践把 RAG 拆成一条六步流水线（综述 arXiv:2312.10997 将其归纳为标准范式），每步都有现成组件，不需要训练任何新模型。图 4 给出全貌：

原创示意图 · 非论文原图
图 4：现代 RAG 系统的六步工程链路。切块 → 嵌入 → 向量库是离线三步，资料入库时做一次（紫色）；召回 → 重排 → 塞进 prompt 是在线三步，每次问答都跑一遍（青色）。与原论文相比，工程链路把「端到端联训」换成了「现成组件拼装」：嵌入模型、向量索引、重排模型各司其职，大模型只在最后读拼接好的输入。

　　逐步看每个环节的要点：

  1. 切块：把长文档切成小块。块太小，一句话被拦腰切断、指代丢失（「该公司」不知指谁）；块太大，相关信号被无关文字稀释，还挤占上下文预算。常见做法是按固定长度重叠切分，或按标题、段落等语义边界切——没有通吃的答案，只能按资料形态调。
  2. 嵌入：每块经嵌入模型压成一个向量。3.1 节讲过词向量的核心性质——语义相近则向量距离相近，这里只是把编码对象从单个词换成整段文本，嵌入模型同样是 Transformer 编码器家族的成员。
  3. 向量库：把所有块的向量建索引存好。库规模大时用近似最近邻（ANN）索引（FAISS 等），拿一点点精度换几个数量级的速度，不必对每个查询都全库精算。
  4. 召回：问题也编成向量，与库内向量算内积或余弦相似度 \(\cos(\mathbf{a}, \mathbf{b}) = \frac{\mathbf{a} \cdot \mathbf{b}}{\|\mathbf{a}\| \, \|\mathbf{b}\|}\)（\(\mathbf{a}\)、\(\mathbf{b}\) 是两个向量，推导见附录 A.2；向量预先归一化时内积与余弦等价），取分数最高的前 \(k\) 个文档块。\(k\) 是经验参数，典型取值在个位数到几十个之间。
  5. 重排：召回求快——文档向量预先算好，一次内积全库扫完；重排求准——换 cross-encoder 精排（把问题与候选块拼成一对、过同一个模型细算相关度，准但慢），只对召回的几十个块运行，所以算得起。两步各司其职。
  6. 塞进 prompt：把筛出的文档块拼在问题前面，一起交给模型。

　　最后一步说穿了就是拼字符串，模型端毫无感知。minimind（Apache 2.0）的 eval_llm.py 把这一事实写得很直白：base 模型是把 bos_token 与 prompt 直接拼成一个字符串（74 行），chat 模型则用 apply_chat_template 拼出带角色标记的字符串（76 行）——不管内容来路如何，模型看到的永远只是拼好的一串 token。RAG 无非在拼接之前多备了一份资料。这也是「RAG 不改权重」的另一种讲法：它只是改变了 prompt 的内容（呼应 14.1，prompt 是模型唯一的输入通道）。代价是上下文变长：第 8 章的长上下文扩展让模型塞得下更多文档块，第 13 章的 KV Cache 与推理优化让长输入算得起。

切块大小是召回质量的第一道关口：切小了断语义，切大了稀释信号、烧上下文预算。拿不准时先用带重叠的固定长度切块打底，再按资料结构（标题层级、表格、代码块）逐步换成语义边界切块，并以召回效果为准迭代。

14.3.4 RAG 的失效模式

　　挂上资料库不等于万事大吉。RAG 系统的失效大多不在生成侧，而在检索与资料侧。Barnett 等人（2024，arXiv:2401.05856）从三个真实项目里总结出七个失效点，排在前两位的分别是「库里本来就没有答案」与「答案在库里但没被召回进 top-k」——都发生在检索一侧。把常见失效归为三类：

  1. 检索不到：正确块根本进不了 top-k。原因可能是嵌入模型的语义盲区（用户措辞与文档措辞差得太远、领域术语分布不同），也可能是库里真的没有。后果是模型只能凭参数记忆硬答——幻觉换了个入口回来。
  2. 切坏上下文：答案横跨两块被拦腰切断，或块内指代断裂、块过大稀释信号。检索到了也对不全、读不懂。
  3. 噪声混入：无关块被模型当真，多个块内容互相矛盾，检索文本里夹带恶意指令。垃圾进，垃圾出，还挤占上下文预算。
失效模式典型原因常见对策
检索不到嵌入模型语义盲区；措辞不匹配；库里没有答案换更适合领域的嵌入模型；向量召回与关键词召回混合；补齐资料库
切坏上下文答案横跨两块被切断；指代断裂；块过大带重叠切块、按语义边界切；命中块顺带取相邻块
噪声混入无关块被当真；多块互相矛盾；恶意指令夹带重排筛掉低分块；要求模型标注引用来源；系统提示约束「仅依据给定资料回答」

　　第三类里有一种值得单独警惕：检索到的文本混进「忽略之前的指令」这类恶意句子，模型可能照做——这叫提示注入，14.4 讲工具调用时还会正面碰上。更根本的提醒是：RAG 没有消灭幻觉，只是把「回答对不对」换成了两个新问题——检索准不准、模型忠不忠于检索到的资料。评估一个 RAG 系统也因此要分两侧打分：检索侧看召回质量，生成侧看答案是否被资料支持。

注释：上下文窗口变大之后，「不如把全文直接塞进去」的议论一直没停。RAG 仍有它的位置：全库塞入的成本随库规模失控，检索则把每次推理的输入控制在窗口预算内，且天然带来出处可追溯的好处。综述（arXiv:2312.10997）对这场争论有系统梳理。

　　至此，模型已经能「开口前先翻书」。但翻书只是单向的读——下一节 Function Calling 让模型反向「打电话」，把请求递出给外部世界执行；14.5 的 Agent 则会把 RAG 当作一件可被调用的工具，组装进多步执行循环。

🧭本节要点回顾
RAG 不改模型权重，为什么能让模型回答训练时没见过的知识？
记忆被拆成两半：参数记忆焊在权重里管语言能力，非参数记忆放在外部向量库管事实知识。RAG 只在推理前把相关文档块检索出来拼进 prompt，改变的只是输入字符串——模型本就只认拼好的 token 流（minimind eval_llm.py 的 74/76 行两种拼法可印证）。资料库随改随生效，权重一个不动。
RAG-Sequence 与 RAG-Token 差在哪？
差在边缘化的层级。RAG-Sequence 整段回答共用同一份检索结果，求和在序列级（公式 (2)）；RAG-Token 每生成一个 token 都重新对 top-k 文档做一次加权，求和钻进连乘号内部（公式 (3)），不同 token 可援引不同文档。今天的工程实践多按前者精神简化：检索 top-k 拼进上下文，交给大模型自己消化。
RAG 系统答错了，排查应该先看哪一侧？
先看检索。七个经典失效点的前两位（库里没有答案、答案没进 top-k）都在检索侧。推荐顺序：库里有没有 → 召回的 top-k 里有没有 → 重排有没有把它顶上来 → 资料是否干净 → 最后才看模型有没有忠于资料生成。
