快速浏览

核心问题子词词表不是人工制定的，而是从语料里学出来的。BPE 用什么规则、按什么顺序把字符一步步合并成子词？
本节主张BPE 分两个阶段：训练阶段统计语料中最高频的相邻符号对并反复合并，学出一个词表和一串有序的合并规则；编码阶段对新文本按同样的顺序贪心应用这些规则。
一句话结论BPE 用“高频片段合并成词、低频词退回字符（或字节）”的策略，在词表大小与序列长度之间取得平衡；byte-level BPE 把基础词表定为 256 个字节，从根上消灭了 OOV。

2.2.1 起源：从数据压缩到神经机器翻译

　　BPE 的全称是 Byte Pair Encoding（字节对编码）。它本来是 1994 年 Philip Gage 发表在 C Users Journal 上的一种数据压缩算法，思路朴素：反复把数据里出现次数最多的相邻字节对替换成一个没用过的新字节，一份数据就能用更少的符号写下来。

　　2016 年，Sennrich、Haddow 和 Birch 在 ACL 论文《Neural Machine Translation of Rare Words with Subword Units》中把这个压缩算法搬到了神经机器翻译里。他们的动机正是 2.1 节讲的 OOV 痛点：翻译系统的词表再大，也总会遇到没收录的稀有词、人名、外来词。BPE 给出的解法是让词表自己从语料中长出来：常见词整块留下，稀有词拆成高频片段，任何词都有出路。此后 BPE 成为神经机器翻译的标配，又被 GPT 系列沿用，成了今天主流 LLM 分词器的基底算法。

BPE（字节对编码） Byte Pair Encoding = 反复合并最高频相邻符号对

BPE 的核心动作只有一个：数数，然后合并。具体数的是：把整个训练语料按目前的拆分方式逐词摆开，从头数出所有相邻符号对各出现了多少次（每个词还要乘上它在语料中的出现次数），把频次最高的那一对捏成一个新符号。这一捏会改变语料的拆分方式，有些原本相邻的符号被吸进了新符号里，相邻关系跟着变了，所以要基于新的拆分再数一遍、再捏一次，如此反复，直到词表长到目标大小。学出来的词表天然是高频片段优先。

就像整理一间办公室：你总是把最常一起使用的两件文具（比如笔和笔帽）装进同一个笔袋，用得越频繁的组合越早被收编，最后桌面上剩下的都是成套的高频组合和零散的低频单件。

2.2.2 训练阶段：手工演算一遍

　　训练 BPE 的目标是学出两样东西：一个词表，和一串有先后顺序的合并规则。算法从字符级开始：先把语料中每个词拆成单个字符，词表初始化为所有出现过的字符；然后进入“统计、合并、更新”的循环。

　　用 Hugging Face LLM Course 第 6 章的经典小例子完整走一遍。假设训练语料只有 5 个词，词频如下：

词hugpugpunbunhugs
出现次数1051245
字符拆分h u gp u gp u nb u nh u g s

　　初始词表是 7 个字符：[b, g, h, n, p, s, u]。接下来逐轮合并：

  1. 第 1 轮：统计所有相邻符号对，按词频加权。u-g 出现在 hug（10 次）、pug（5 次）、hugs（5 次）中，共 20 次，全场最高。合并 u + g 得到新符号 ug，加入词表。
  2. 第 2 轮：更新拆分后重新统计。u-n 出现在 pun（12 次）、bun（4 次）中，共 16 次，最高。合并 u + n 得到 un。
  3. 第 3 轮：h-ug 出现在 hug（10 次）、hugs（5 次）中，共 15 次，最高。合并 h + ug 得到 hug。

　　此时假设词表达到了目标大小，训练停止。最终词表为 [b, g, h, n, p, s, u, ug, un, hug]，合并规则按学习顺序记录为 (u,g)→ug、(u,n)→un、(h,ug)→hug。注意规则的顺序本身就是训练产物，编码时要严格按这个顺序应用。

原创示意图 · 非论文原图
图示：在 hug×10、pug×5、pun×12、bun×4、hugs×5 的玩具语料上，BPE 三轮合并依次产出 ug、un、hug 三个新符号。
BPE 学到的词表是频率驱动的：出现得越多的片段越早成为独立 token。这意味着训练语料的构成直接决定词表的长相，换一批语料就要重新训练分词器，不能拿来即用。

2.2.3 编码阶段：按合并顺序贪心应用

　　词表和合并规则学好后，编码一个新词的方法是先把它拆成字符，再按训练时学到的先后顺序逐条尝试合并规则，能合就合，不能合就跳过：

  • bug：拆成 b、u、g。第 1 条规则 (u,g)→ug 适用，得到 b、ug；后两条规则不适用。最终切分为 b + ug。bug 这个词从未在训练语料里出现，但借助 ug 这个片段被顺利表示，这正是子词泛化能力的体现。
  • hugs：拆成 h、u、g、s。应用 (u,g)→ug 得 h、ug、s；再应用 (h,ug)→hug 得 hug、s。最终切分为 hug + s。
  • 没参与任何合并的字符保留原样，落回基础词表里的单字符 token。

　　因为基础词表覆盖了语料中所有字符，这个例子里不存在编码失败的词。真实分词器还会先做预切分（比如按空格和标点把句子切成词），再在每个片段内部跑上述合并流程。

2.2.4 训练算法伪代码

　　把上面的过程写成算法，就是下面这个循环：

function 训练BPE(语料, 目标词表大小):
    词频表 ← 统计语料中每个词的出现次数
    拆分表 ← 每个词拆成字符序列
    词表   ← 所有出现过的字符
    合并规则 ← 空列表
    while 词表大小 < 目标词表大小:
        频次表 ← 按词频加权，统计拆分表中所有相邻符号对的频次
        (A, B) ← 频次最高的符号对
        词表   ← 词表 ∪ {AB}          # 新符号入词表
        合并规则 ← 合并规则 + [(A, B)]  # 顺序即优先级
        拆分表 ← 所有 (A, B) 替换为 AB  # 更新拆分，进入下一轮
    return 词表, 合并规则

　　编码函数同样简单：把输入拆成字符后，从合并规则列表的第一条开始扫描，凡是能应用的就应用，直到没有规则可匹配。两份产物合在一起就是一个完整的 BPE 分词器。

2.2.5 Byte-level BPE：GPT-2 的选择

　　字符级 BPE 有一个隐蔽的漏洞：基础词表是“语料里出现过的字符”。多语言场景下字符集极大，汉字、 emoji、各种变音符号加起来数以万计，基础词表还没开始合并就已经很臃肿，而且语料里没出现过的字符依然会 OOV。

　　GPT-2（Radford et al., 2019）给出的解法是把 BPE 直接跑在 UTF-8 字节上，称为 byte-level BPE：

  • 任何文本按 UTF-8 编码后都是一串字节，字节只有 256 种取值，所以基础词表固定为 256 个字节，与语料无关；
  • 汉字、emoji、乱码、罕见符号都能拆成字节表示，从机制上杜绝了 OOV；
  • GPT-2 的词表大小为 50257：256 个字节 + 50000 条合并规则学出的符号 + 1 个特殊 token。
Byte-level BPE 在 UTF-8 字节序列上运行的 BPE

合并的对象从字符换成字节，其余逻辑一字不改。好处是基础词表恒定 256 且对任意文本封闭：一个汉字在 UTF-8 下占 3 个字节，即使词表里没有这个汉字本身，也总能用字节把它拼出来。

就像快递公司不保证认识每个收件人，但保证认识所有门牌号的数字。只要地址能写成数字（字节），包裹（文本）就永远送得到。

　　工程实现上，OpenAI 开源的 tiktoken 是 GPT 系列模型的官方 byte-level BPE 分词器，用 Rust 实现、速度极快；想读一份短小清晰的教学实现，可以看 Andrej Karpathy 的 minbpe，几百行 Python 完整复现了训练与编码两条路径。

词表大小是一个超参数，由人在训练分词器前指定，不是算法学出来的。BPE 学到的是“在这个预算下选哪些合并”。词表越大，平均序列越短、语义越完整，但 Embedding 层参数越多、稀有 token 训练越不充分；主流 LLM 的取值从 3 万到 25 万不等。GPT-2 选了 5 万条合并，只是一个具体的工程取值。

　　BPE 的故事到这里就完整了：一个压缩算法被改造成词表学习器，又在字节层面补上了最后的 OOV 缺口。下一节看另外两条子词路线：WordPiece 和 Unigram，它们换了合并（或剪枝）的评分标准，思路各有千秋。

🧭本节要点回顾
BPE 为什么要先训练学规则，再谈编码？
词表和合并顺序是从语料频率中学出来的，编码只是按学到的顺序贪心重放。没有这个顺序，同一串字符可能有多种合并不确定性，切分结果就不唯一，模型输入也就不稳定。
byte-level BPE 为什么能彻底杜绝 OOV？
任何文本按 UTF-8 编码后都是字节序列，而字节只有 256 种，全部收进基础词表。再罕见的字符、再新的词都能拆成字节兜底，不存在词表之外的输入。
词表大小由什么决定？
它是人工设定的超参数：训练时合并到目标大小就停（如 GPT-2 的 50000 条合并加 256 字节加 1 个特殊 token）。取值要在序列长度、Embedding 参数量和稀有 token 训练充分性之间权衡。
